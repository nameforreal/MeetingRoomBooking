# Разграничение доступа

Административный доступ требует активной учётной записи, `is_staff=True`
и разрешения на конкретную операцию. Группы сами не устанавливают `is_staff`.
Активный суперпользователь с `is_staff=True` сохраняет полный доступ.

| Группа | Разрешения |
|---|---|
| Booking Viewers | `rooms.view_booking`, `rooms.view_room` |
| Booking Managers | `rooms.view_booking`, `rooms.change_booking`, `rooms.view_room` |
| Room Managers | `rooms.view_room`, `rooms.add_room`, `rooms.change_room` |
| User Managers | `auth.view_user`, `auth.change_user` |
| Operations Administrators | Объединение Booking Managers, Room Managers и User Managers |

Ни одна роль автоматически не получает экспорт, физическое удаление,
назначение групп, разрешений или прав суперпользователя.

## Карта операций

| Операция | Разрешение |
|---|---|
| Обзор и аналитика бронирований, список всех бронирований | `rooms.view_booking` |
| Подтверждение и отмена чужих заявок | `rooms.change_booking` |
| Экспорт CSV в обеих панелях | `rooms.export_booking` |
| Список комнат в панели, архивные комнаты API | `rooms.view_room` |
| Создание комнаты | `rooms.add_room` |
| Изменение, архивирование и восстановление комнаты | `rooms.change_room` |
| Физическое удаление комнаты через Django Admin | `rooms.delete_room` |
| Просмотр пользователей | `auth.view_user` |
| Редактирование обычного аккаунта | `auth.change_user` |

Стандартные добавление, изменение и удаление бронирований в Django Admin
проверяют соответствующие модельные разрешения. Роли не получают
`add_booking` и `delete_booking` автоматически.

User Managers могут изменять имя, фамилию, email и активность обычного
пользователя. Собственную запись, сотрудников и суперпользователей изменяет
только суперпользователь. В Django Admin также закрыты изменение паролей,
создание и удаление аккаунтов для несуперпользователей. Назначение ролей,
permissions и административных флагов доступно только суперпользователю.

Публичный каталог и занятость активных комнат остаются публичными.
`GET /api/rooms/?include_archived=true` требует `rooms.view_room` и признака
сотрудника. Для восстановления: `PATCH /api/rooms/<id>/` с
`{"is_active": true}`. `DELETE` архивирует, поэтому требует `change_room`.
API бронирований по-прежнему возвращает только собственные записи:
административные группы не расширяют этот queryset.

## Первоначальная настройка

После проверки резервной копии и в согласованное время администратор выполняет:

```powershell
python manage.py migrate
python manage.py setup_roles
```

Миграция `0004_booking_export_permission` добавляет описание отдельного права
экспорта. Django создаёт Permission при `post_migrate`.
Эти команды при реализации на рабочей базе не запускались.

`setup_roles` идемпотентна: создаёт отсутствующие группы и добавляет явно
перечисленные права. Не удаляет дополнительные права и участников существующих
групп, не назначает роли пользователям и не меняет административные флаги.
Поэтому уже существующие дополнительные права групп нужно проверить вручную.

Суперпользователь назначает сотруднику нужные группы через Django Admin.
Экспорт выдаётся отдельно как `rooms.export_booking`; для экспорта через
Django Admin также нужен доступ к списку бронирований.

## Изолированная проверка

```powershell
python -B manage.py check --settings=config.test_settings
python -B manage.py test --settings=config.test_settings --noinput
python -B manage.py makemigrations --check --dry-run --settings=config.test_settings
```

Эта конфигурация не импортирует рабочие настройки и не читает `.env`.
Из исходника настроек извлекаются только разрешённые литеральные параметры
приложений, шаблонов и middleware. База — SQLite исключительно в памяти;
миграции проверяются только на ней. Ускоренный хешер предназначен исключительно
для тестов. Не используйте `config.test_settings` для запуска приложения.

Проверки PostgreSQL-блокировок, бизнес-логика VIP-переносов, конкурентных
изменений и остальные находки аудита относятся к последующим этапам.
