# Сохранность истории и журнал событий — этап 5.4

Реализовано поверх контрольной точки `4f84a2e`. Revision, ключи создания,
VIP-согласование и существующие Groups/Permissions сохраняют свои контракты.
Этот документ дополняет BUSINESS_RULES.md, API_GUIDE.md и CONCURRENCY.md.

## Политика удаления

- Booking нельзя физически удалить через Model.delete(), QuerySet.delete(),
  API или Django Admin, включая одиночные и массовые действия суперпользователя.
  Защита относится и к отменённым, завершённым и старым бронированиям.
- Booking.room и Booking.user используют PROTECT. Новые события защищают
  также прежние комнаты и владельцев после переноса или смены владельца.
- Комнаты архивируются; пользователи деактивируются. Это не отменяет и не
  удаляет их существующие и будущие встречи. Повтор установки того же состояния
  не создаёт события. Панель управления передаёт явное целевое `is_active`,
  поэтому повтор POST архивирования не восстанавливает комнату.
- Удаление Room/User через обычный ORM и Admin запрещено даже без бронирований.
  Для действительно пустых объектов существует отдельная служебная процедура
  `rooms.retention.delete_empty(obj, actor=...)`, доступная активному
  суперпользователю. HTTP-пути для неё нет. Самоудаление запрещено.
- Процедура под блокировками проверяет бронирования, новые события, прежние
  связи из событий, результаты идемпотентного создания и старые LogEntry.
  При наличии истории — ProtectedError. При разрешённом удалении сохраняется
  событие с типом и ID удалённого объекта без FK на него; автор защищён PROTECT.
  Ошибка записи этого события откатывает удаление.

## AuditEvent

| Поля | Назначение |
|---|---|
| occurred_at, action | Время фиксации и тип успешной операции |
| source, actor | html / api / django_admin / management / system и автор |
| object_type, object_id | Тип и ID целевого объекта |
| booking, room, subject_user | Ссылки на цель события, PROTECT |
| previous_room, new_room, previous_owner, new_owner | Защищённые ссылки на прежние и новые связи брони |
| before, after, changed_fields | Минимальные состояния и имена изменившихся полей |
| revision_before, revision_after | Версия брони до и после записи |
| correlation_id, schema_version | Связь событий одной операции/массового действия и версия формата |

Снимок брони содержит только ID комнаты/владельца, UTC-время начала/окончания,
статус и revision. Снимок комнаты — is_active/is_vip, пользователя — is_active.
Пароли, токены, ключи идемпотентности, имена, email, произвольный payload или
тексты запросов не записываются. Автор может быть NULL только у source=system.
Контекст задаётся сервером; клиент не назначает источник, автора и correlation_id.
Внутренние Python-вызовы вне HTTP имеют source=system; явный actor сохраняется,
а его отсутствие означает системную операцию, не попытку угадать автора.

Индексы: время/ID, автор/время, действие/время, correlation_id/ID; FK индексируются
Django. Уникальные ограничения разрешают одно обычное событие на пару
booking/revision_after и один baseline на бронь. Baseline не конфликтует с
обычным событием той же версии. Проверки БД ограничивают source и наличие автора.

Основные действия: booking.created, time_changed, room_changed, owner_changed,
updated (несколько полей), saved (обычное сохранение увеличило только revision),
cancelled, confirmed, vip_rejected, approval_reset; room.archived/restored/
type_changed; user.activated/deactivated; room.deleted/user.deleted для пустых
объектов. У действий брони префикс `booking.`. Изменение комнаты и статуса одной
записью — booking.updated с обоими полями в changed_fields. Редактирование только
имени/описания комнаты или профиля пользователя не копирует их в бизнес-журнал.

## Атомарность и конкурентные операции

События создаются общим `rooms.audit.record` только внутри бизнес-транзакции.
Booking и Room используют существующий booking_operations. Пользователи —
новый account_operations. Интерфейсы устанавливают контекст, но не пишут
отдельные события после commit. Ошибка события откатывает бизнес-изменение.

Порядок создания остаётся: ключ → комнаты по ID → бронь → событие и результат
создания → COMMIT. Редактирование: комнаты по ID → бронь → событие. Изменение
типа комнаты: комната → затронутые брони по ID → события в общей транзакции.
Массовое согласование сохраняет отдельные транзакции по строкам: один
correlation_id связывает успешные результаты; отказавшие строки событий не имеют.
Повтор создания возвращает исходный снимок без записи AuditEvent/LogEntry и без
увеличения revision, в том числе после отмены, переноса и неизвестного COMMIT.
Повтор отмены по существующему контракту также не пишет событие.

Сервис пользователя блокирует целевую строку FOR NO KEY UPDATE на PostgreSQL.
Это совместимо с FK-проверками автора и не вызывает взаимную блокировку, когда
два администратора одновременно изменяют активность друг друга. Контролируемое
удаление пользователя блокирует пользователя и исполнителя по ID. При удалении
комнаты сначала блокируется комната, как в бронировании. Бизнес-проверки и
запись журнала выполняются до освобождения блокировок.

Неудачные вызовы операций пишут техническое предупреждение в logger
`rooms.operations`: имя операции и класс исключения, без payload/ключа/текста
исключения. Бизнес-журнал содержит только зафиксированные операции.

## Защита стандартного User на PostgreSQL

BEFORE UPDATE-триггер auth_user.is_active отклоняет реальную смену значения
без разрешения сервиса, в том числе через QuerySet.update(), bulk_update()
и обычный Model.save(). Ошибка PostgreSQL имеет SQLSTATE 42501. Изменение
других полей и запись прежнего is_active разрешены; вставка нового User остаётся
стандартной. Модель User, Groups и система разрешений не заменяются.

Сервис под блокировкой устанавливает `set_config(..., true)` для
`meetingroom.user_activity`: текущая транзакция + ID пользователя + целевое
булево значение. Триггер сравнивает все три части, отсутствие/несовпадение
запрещает запись. После UPDATE прежнее значение восстанавливается сразу, а
savepoint обеспечивает восстановление и при ошибке SQL. Разрешение нельзя
использовать для другой строки/значения, последующего ORM-запроса либо новой
транзакции. Глобальные настройки PostgreSQL не меняются.

На SQLite триггер не устанавливается; сервис, журнал и интерфейсы работают,
но SQLite не доказывает защиту прямого изменения User.is_active или работу
SELECT FOR UPDATE. Эти проверки выполняются только на PostgreSQL 17.

## Неизменяемость и просмотр

AuditEvent запрещает обычные ORM save/create/update/delete, bulk_create,
bulk_update и update_or_create; запись доступна внутреннему сервису.
Admin предоставляет только просмотр (список по 50, фильтры, поиск, детали).
Суперпользователь может просматривать; сотруднику нужно rooms.view_auditevent.
Разрешение новым или существующим группам автоматически не назначается.
Добавление, редактирование и удаление через Admin запрещены и суперпользователю.
Ссылка «История» у брони/комнаты/пользователя ведёт на отфильтрованный журнал
с той же проверкой доступа. Старые LogEntry сохраняются.

Граница доверия — обычные ORM и HTTP-интерфейсы. Владелец БД с произвольным SQL,
отключением триггеров или Python-код с явным вызовом базового Model.save являются
доверенными инструментами обслуживания. Этот этап не вводит отдельного DB-role
для запрета SQL UPDATE/DELETE журнала. Транзакционный маркер защищает штатный ORM
от обхода сервиса, но не является секретом от владельца SQL-соединения.

## Миграции и baseline

1. 0007_audit_history: схема AuditEvent, индексы/ограничения, PROTECT у Booking,
   настройки менеджера Room. Создаётся только permission view_auditevent.
2. 0008_booking_baselines: для каждой существующей брони снимок известного
   состояния; action=baseline, source=system, actor=NULL, before={},
   revision_before=NULL. occurred_at — время миграции, а не выдуманное время
   прежнего изменения. Автор и неизвестные прошлые владельцы/комнаты не
   восстанавливаются. Запись партиями по 500; повторный запуск не дублирует baseline.
3. 0009_user_activity_guard: установка PostgreSQL-функции и триггера. Дополнительное
   расширение не требуется. Обратная миграция снимает триггер и функцию.

При будущем развёртывании следует остановить старые процессы записи, сделать
резервную копию и применить миграции до запуска нового кода: иначе старый код
не пишет журнал и несовместим с защитой is_active. Для большой истории нужно
заранее оценить длительность миграции baseline. На рабочую БД этот этап миграции
не применял. Проверки выполнялись только на изолированных тестовых базах.

В этапе 5.6.2 добавлены ранние проверки reverse. При наличии Booking,
BookingCreationRequest или AuditEvent откат 0009 запрещается ещё до снятия
триггера; аналогичные проверки защищают предыдущие этапы. Baseline не удаляется
и миграция 0008 не помечается отменённой при наличии истории. Пустая установка
может быть полностью отменена и установлена заново. Автоматической очистки/TTL нет.
Подробности и backup/restore: [MIGRATION_SAFETY.md](MIGRATION_SAFETY.md).
