# Бизнес-правила MeetingRoomBooking — этапы 5.1–5.3

## Статус документа

Этап 5.1 изменил только документацию. Этап 5.2 реализует обязательную revision
для изменения и согласования существующих броней во всех интерфейсах, включая
отмену и массовые действия. Этап 5.3 реализует ключи создания для HTML, API и
Django Admin. Полная политика сохранения истории и изменение переноса
VIP → обычная остаются отдельными задачами.
Источник бизнес-контрактов — этот документ. [VIP_APPROVAL.md](VIP_APPROVAL.md)
уточняет согласование, [CONCURRENCY.md](CONCURRENCY.md) — транзакции,
[API_GUIDE.md](API_GUIDE.md) — текущий API и будущие изменения совместимости.

Разделы A–E фиксируют утверждённое поведение. Технические контракты описывают
требования к будущей реализации. Расхождения с кодом и решения, требующие
согласования, перечислены отдельно. Результаты тестов этапа 4 исторические:
в этапе 5.1 тестовые базы не создавались, тесты и миграции не запускались.
Проверки этапа 5.2 описаны в отдельном разделе ниже.

## Принятые значения

Источник правил — `rooms/booking_rules.py`. Значения взяты из существующей
модели, формы бронирования, расписания и настроек проекта:

| Правило | Значение |
|---|---|
| Часовой пояс хранения | UTC |
| Часовой пояс сайта | `settings.TIME_ZONE`, сейчас UTC |
| Рабочий день | 08:00–20:00, начало и окончание в один местный день |
| Длительность | От 1 до 4 часов включительно |
| Горизонт | Сегодня — сегодня + 30 дней включительно |
| Начало | Не раньше текущего момента |
| Сетка расписания | Один час; частично занятый час отображается занятым |
| Произвольное время | Допустимо внутри рабочего дня; округление не выполняется |

В старом расписании был горизонт 60 дней, хотя форма бронирования принимала
выбор даты только на 30 дней. Теперь расписание, форма, API доступности и
серверная проверка новых/перенесённых встреч используют 30 дней.
Часовые слоты остаются способом отображения и быстрого заполнения формы:
начало в 10:15 и длительность 90 минут допустимы, как и раньше.

UTC сохранён: переключения сайта на московское время не было. API принимает
ISO 8601 со смещением и преобразует момент в часовой пояс сайта перед проверкой
рабочих часов. Корректное `+03:00` допустимо; некорректные часы/минуты смещения
и неизвестные названия зон отклоняются. Значение без смещения в API и HTML
интерпретируется в часовом поясе сайта. Прямой вызов модели требует aware datetime.
Переопределение текущей зоны отдельного запроса не меняет бизнес-календарь.

## Обработка дат

- Календарные GET-параметры имеют строгий формат `YYYY-MM-DD`.
- Несуществующие даты, пустые переданные значения и неверный формат дают HTTP 400
  в API. HTML показывает сообщение и возвращает безопасный период по умолчанию.
- Отсутствие даты в HTML означает сегодня; отсутствие фильтров списка API
  означает отсутствие фильтра. Дата в API доступности обязательна.
- Для исторических фильтров разрешён технический диапазон от `0001-01-02`
  до `9999-12-30`: оставлен запас для преобразования зоны и следующих суток.
- Доступность комнат дополнительно ограничена горизонтом бронирования.
- Обратный диапазон фильтра API возвращает 400. Аналитика сохраняет ограничение
  периода в 366 календарных дней и сообщает об ошибке периода в HTML.
- HTML-поля даты выводятся в ISO-формате, пригодном для `input[type=date]`.
- Ошибки дат, datetime и смещений, включая переполнение, не становятся ответами 500.

Проверки прошлого времени, горизонта и рабочих часов применяются при создании
или изменении комнаты/времени. Изменение только статуса не переписывает старые
интервалы и не требует соответствия исторической записи новому горизонту.
Порядок времени и длительность по-прежнему проверяются моделью.

## Активность, отмена и согласование

Активность комнаты повторно читается под блокировкой перед записью.
Архивирование не удаляет бронирования. Новые брони и изменения в архивной
комнате запрещены; отмена существующей брони разрешена.

Сохранена политика этапа 3: владелец или уполномоченный сотрудник может отменить
ожидающую, подтверждённую или завершённую встречу. Повторная отмена идемпотентна.
Отменённая запись не редактируется и не восстанавливается. HTML, API, собственная
панель и Django Admin используют один слой операций. Кнопка отмены теперь
доступна и для завершённой встречи; редактирование завершённой скрыто и запрещено.

При смене обычной комнаты на VIP:

1. Блокируется комната.
2. Выбираются ещё не завершённые `confirmed` бронирования и блокируются по ID.
3. Они переводятся в `pending`; `revision` каждой записи увеличивается.
4. Тип комнаты и все изменения заявок фиксируются одной транзакцией.

Уже начавшиеся, но не завершённые встречи тоже требуют согласования; сотрудник
с `change_booking` может подтвердить такую неизменённую заявку до её окончания.
Завершённые и отменённые записи не меняются. Переход VIP → обычная комната
сохраняет статусы и не подтверждает ожидающие заявки автоматически.

Этот механизм действует через API комнат, обе административные панели и
`Room.save()`. Массовые обновления `is_vip`/`is_active`, включая bulk upsert,
запрещены у стандартного менеджера. Приватные ORM-механизмы и прямой SQL остаются
доверенными инструментами сопровождения, которые нельзя использовать для
обхода слоя операций.

## Утверждённые бизнес-правила этапа 5.1

### A. Версия существующего бронирования

- При редактировании, переносе, подтверждении, отклонении и отмене запрос
  обязательно содержит версию записи, которую пользователь видел на странице
  или получил в ответе API. Создание новой записи не требует исходной revision.
- Отсутствующая, пустая или некорректная версия — ошибка валидации. Версия —
  целое неотрицательное число; клиент передаёт полученное значение, а не
  вычисляет следующее. Нулевые версии старых записей не исключаются произвольно.
- Перед изменением версия должна совпасть с актуальной версией под блокировкой.
  Несовпадение означает отказ без изменения записи. Исключение без изменения
  состояния — повторная отмена уже отменённой записи, точно определённая в D.
- Нельзя подставлять текущую версию вместо отсутствующей клиентской, автоматически
  обновлять её перед повторной отправкой или перезаписывать более свежие данные.
- Правило одинаково для REST API, HTML, Django Admin и собственной панели,
  включая массовые действия. Скрытое поле само по себе не заменяет проверку.
- Revision меняет только сервер; успешно зафиксированное изменение состояния
  увеличивает её. Отказ и идемпотентная повторная отмена не увеличивают revision.
- Версия не заменяет проверку владельца, permissions, статуса, времени и комнаты.

### B. VIP-согласование

- Новая VIP-заявка получает `pending`. Подтверждение остаётся ручным и требует
  активного сотрудника с `rooms.change_booking`; пользователь не подтверждает
  собственную VIP-заявку через пользовательские HTML/API-операции.
- Согласование относится к просмотренной версии и её параметрам: комнате,
  началу и окончанию. Изменение комнаты или времени VIP-заявки требует нового
  согласования; перенос подтверждённой VIP-встречи переводит её в `pending`.
- Формулировка задания о переносе VIP-встречи применяется и к переносу из VIP
  в обычную комнату: прежнее согласование не переносится автоматически.
  Это расширяет текущее поведение кода; расхождение отмечено ниже.
- Перенос из обычной комнаты в VIP также требует `pending`. Перенос ожидающей
  заявки в обычную комнату не подтверждает её автоматически. Обычная новая бронь
  получает `confirmed`; перенос между обычными комнатами сохраняет статус.
- Сохранение без изменения комнаты/времени не сбрасывает согласование, но
  запрос изменения существующей записи всё равно обязан передавать revision.
- Подтверждение выполняется отдельно от редактирования. Устаревшую заявку
  нельзя согласовать, даже если её статус всё ещё `pending`. Сотрудник должен
  заново увидеть изменившиеся параметры и выполнить новое явное действие.
- Массовое согласование проверяет версию каждой выбранной заявки. Нельзя
  получать версии только в момент POST и считать их просмотренными.
- Правила смены типа самой комнаты из этапа 4 сохраняются: обычная → VIP
  переводит незавершённые `confirmed` в `pending` и увеличивает revision;
  VIP → обычная не подтверждает ожидающие заявки. Завершённая история не меняется.

### C. Удаление и сохранение истории

- История включает все статусы и даты, в том числе отменённые бронирования.
- Комната с любой историей бронирований архивируется, а не удаляется физически.
- Пользователь с любой историей деактивируется, а не удаляется физически.
- Удаление связанных объектов не должно удалять бронирования каскадом.
- Ни одиночное, ни массовое физическое удаление бронирований через Admin
  не может служить обходом хранения истории. До отдельной политики очистки
  административное действие должно отменять запись, а не удалять её.
- Эти ограничения действуют и для суперпользователя. Полнота его permissions
  не означает право обходить бизнес-правила хранения и согласования.
- Рекомендуемое техническое решение — `PROTECT` для обеих связей Booking
  плюс ограничения административных операций. Оно потребует миграции;
  переопределения одной кнопки или одного `save()` недостаточно.
- Удаление объектов без истории, сроки хранения и обезличивание требуют
  отдельного согласования. Этап 5.1 не вводит автоматическую очистку данных.

### D. Отмена и повторная отмена

Отменить можно ожидающую, подтверждённую, уже начавшуюся или завершённую встречу
при наличии права на эту операцию. Неактивная комната не препятствует отмене.
Запись сохраняется, статус становится `cancelled`; восстановления нет.

Технический контракт отмены после проверки доступа, формата revision и получения
блокировок:

| Актуальное состояние | Переданная версия | Результат |
|---|---|---|
| Любое | Отсутствует или некорректна | Ошибка валидации, ничего не менять |
| `pending` / `confirmed` | Не совпадает | Отказ как для устаревшей записи |
| `pending` / `confirmed` | Совпадает | Одна отмена, одно увеличение revision; одно событие после внедрения журнала |
| `cancelled` | Корректна, совпадает или устарела | Успешный повтор без записи, увеличения revision и нового события |
| `cancelled` | Больше текущей версии | Отказ: такая версия не могла быть исходной для повтора |

Разрешение старой версии в строке успешного повтора не разрешает изменять
устаревшую запись: состояние уже достигнуто, обновления нет. Обязательная
передача версии сохраняется и для повторного запроса. Проверка доступа также
сохраняется: нельзя раскрывать чужую отменённую бронь.

Если подтверждение или перенос увеличили revision раньше отмены, отмена со
старой версией отклоняется. Если первой прошла отмена, подтверждение/перенос
отклоняются. Прежняя гарантия «отмена всегда побеждает подтверждение» больше
не является целевым контрактом. Общий порядок блокировок при этом сохраняется.

### E. Повтор создания и ключ идемпотентности

- Область ключа: авторизованный пользователь + операция создания бронирования
  + ключ. Ключ одного пользователя не предоставляет доступ к результату другого.
- Тот же ключ с теми же данными возвращает первоначальный успешный результат
  создания, включая идентификатор брони; новая запись не создаётся.
- Тот же ключ с другими данными отклоняется без изменения первоначальной брони.
- Конкурентные повторы одного ключа не создают дубли; результат и запись брони
  должны фиксироваться согласованно. Сбой до фиксации не оставляет ложный успех.
- Перенос или отмена созданной брони не освобождают её ключ для нового создания.
  Повтор не восстанавливает отменённую запись. Для нового намерения нужен новый ключ.
- Первоначальный результат не является свежим состоянием брони. Перед её
  последующим изменением клиент получает актуальные данные и revision.
- Ключ идемпотентности не заменяет revision, проверку доступа и CSRF.

Технический контракт совместимости API и HTML:

| Интерфейс | Будущая передача и повтор |
|---|---|
| REST API | Клиент сохраняет ключ на время одного намерения создания и повторяет его при неизвестном результате запроса |
| HTML | Форма получает скрытый ключ; двойное нажатие и повтор той же отправки используют один ключ; новое намерение получает новый |
| Оба | Одна область ключей и один слой операций; смена интерфейса не разрешает повторное создание по уже использованному ключу |

В этапе 5.3 реализованы обязательные заголовок `Idempotency-Key` и скрытое поле
`idempotency_key`; утверждённые параметры приведены в разделе реализации 5.3 ниже.
API должен воспроизводить первоначальный результат создания, HTML — завершать
тот же сценарий успеха без повторного создания и события. Представления могут
отличаться: JSON в API и редирект в HTML; воспроизводить старые cookies/CSRF
не требуется. Правило действует и для повторов между интерфейсами.
Сравнивать нужно значимые данные, а не CSRF-токен или формат JSON. Детали
нормализации, ошибок и перехода клиентов описаны в API_GUIDE.md и разделе 5.3.

## Технические контракты и статус реализации

В этапе 5.2 реализованы проверки revision, версии массовых действий и повторная
отмена. В этапе 5.3 реализованы ключи создания. Будущий единый журнал событий
и полная защита удаления пока не реализованы. LogEntry Django Admin не дублируется
при повторной отмене и повторном создании.

- Сохраняются транзакции и порядок блокировок: комнаты по ID, затем бронирования.
  Проверки доступа, актуального состояния, версии и активности выполняются
  до записи под соответствующими блокировками. Старые поля не восстанавливаются.
- Автоматический сброс согласования при смене типа комнаты — внутренняя
  операция: берёт текущие версии затронутых броней под блокировкой и увеличивает
  их, а не требует от администратора версии всех броней. Это не разрешает
  заменять клиентскую revision в обычном запросе редактирования/подтверждения.
- Сохраняются отдельные транзакции массовых действий и явные результаты по
  каждой записи. Устаревший элемент отклоняется; корректные могут выполниться.
  Выбор «всех результатов поиска» не должен подтверждать непросмотренные версии:
  понадобится предварительный просмотр или иной явный этап ознакомления.
- `pending` и `confirmed` занимают интервал, `cancelled` — нет. Соседние
  полуоткрытые интервалы разрешены. PostgreSQL-ограничение пересечений сохраняется.
- Права определяются Django Permissions и группами. Активный суперпользователь
  управляет всеми доступными возможностями в рамках бизнес-правил; менеджер —
  только выданными разрешениями. Один `is_staff` полномочий не предоставляет.
  Существующие группы и permissions не переопределяются этим документом.
- Будущий журнал фиксирует только состоявшиеся изменения; отказ и успешная
  повторная отмена не добавляют новых событий изменения состояния. Технический
  журнал HTTP-запросов может фиксировать повторы отдельно.

## Решения, требующие дополнительного согласования

1. В 5.3 согласовано хранение без автоматического TTL. Будущие ограничение объёма,
   обезличивание и очистка потребуют нового контракта: удаление ключа может
   разрешить дублирование при позднем повторе.
2. В 5.3 ключ обязателен во всех интерфейсах создания, без режима совместимости.
   Порядок выпуска у внешних клиентов согласуется отдельно; API_GUIDE.md описывает
   несовместимое изменение и формат ключа.
3. Канонизация и ответы повтора утверждены и реализованы в 5.3 (см. ниже).
4. Общая унификация HTTP-кодов и машинных ошибок, форма ошибок и политика
   выпуска несовместимых изменений. Сейчас ошибки версии API имеют код 400;
   переход на 409 не утверждён. Обязательность revision уже реализована в 5.2:
   текущий код не поддерживает старые запросы изменения без версии. Порядок
   развёртывания обновления у внешних клиентов необходимо согласовать отдельно.
5. Физическое удаление комнат/пользователей без истории; сроки хранения истории,
   обезличивание и доступ к персональным данным. `PROTECT` — рекомендуемый
   механизм, окончательные миграции требуют отдельного рассмотрения.
6. Правила изменения владельца брони через Admin и влияние такого изменения
   на согласование: это отдельный вопрос сверх текущего переноса комнаты/времени.

## Реализация этапа 5.3: создание с ключом

Все HTTP-пути создания вызывают `booking_operations.create_once()`, использующий
`booking_idempotency`. Уникальность: actor + `booking.create` + key. Ключ обязателен,
1–128 ASCII-символов `[A-Za-z0-9._:-]`, регистр значим; UUIDv4 рекомендован.
HTML/Admin генерируют ключ при GET без записи в БД и сохраняют его при ошибках POST.

`BookingCreationRequest` хранит actor (PROTECT), операцию, ключ, версию нормализации,
канонические параметры и SHA-256, booking (PROTECT), первоначальное тело ответа,
HTTP-статус, версию ответа и времена создания/завершения. Состояние резервирования
определяется пустыми booking/response_payload/completed_at; оно существует только
в незавершённой транзакции. Снаружи доступны только завершённые записи.
Успешное завершение атомарно с бронью; LogEntry Admin включён во внешнюю транзакцию
Admin. Ошибка до COMMIT откатывает всё. Повтор не вызывает save и не увеличивает revision.

Значимые данные: фактический владелец, ID комнаты, начало/конец в UTC с точностью
до микросекунд. Статус вычисляется сервером по существующим правилам. Снимок ответа
содержит только поля публичного Booking API, без имени/email владельца.
Повтор проходит авторизацию заново, включая доступ к актуальной брони; потеря
доступа даёт отказ. Смена интерфейса не меняет область ключа.

Ключ закрепляется первым успешным COMMIT. Ошибки не кешируются; исправленная
операция может использовать ключ полностью откатившейся попытки. Нет TTL,
автоматической очистки и повторного использования успешного ключа. Новые FK
PROTECT также блокируют каскадное удаление связанных с результатом объектов;
это не заменяет будущую политику хранения всех старых бронирований.
Обычные save/update/delete/bulk-операции для записей ключей запрещены; доверенный
внутренний код сохраняет их только в общем транзакционном механизме.

API: 201 при создании и повторе, 400 при отсутствии/ошибке формата ключа,
409 при других данных, 503 и Retry-After: 1 после пяти секунд ожидания ключа.
Старые клиенты обязаны начать передавать Idempotency-Key. Исторические бронирования
не получают ключей задним числом. Revision и VIP-подтверждение не подменяются replay.

Миграция 0006 создаёт только новую таблицу, FK и ограничения; старые данные,
revision, Groups/Permissions и PostgreSQL-ограничение пересечений не меняет.
Рабочая база, .env, настройки подключения и CSS в этапе не затрагиваются.
