# Конкурентные операции бронирования

## Статус документа

Базовый механизм реализован в этапах 3–4. Этап 5.1 зафиксировал контракты,
этап 5.2 добавил обязательную клиентскую revision для всех изменений существующей
брони и согласования. Источник правил — [BUSINESS_RULES.md](BUSINESS_RULES.md),
разделы A–E. Этап 5.3 реализует ключи создания. Полная защита удаления
и единый журнал остаются будущими задачами.

## Общий механизм после этапа 5.2

`rooms.booking_operations` используется HTML, API, Django Admin и собственной
панелью. Он содержит `create`, `edit` (время и комната), `cancel`, `confirm`,
`reject` и внутренний `persist`. `Booking.save(revision=...)` также проходит через
`persist`; проверка интервалов и VIP-статусов остаётся общей модельной проверкой.
HTTP-пути проверяют владельца/permissions; вызов `save()` из Python считается
доверенным внутренним кодом, а не способом авторизации пользователя.

Порядок для одной операции:

1. Начать `transaction.atomic()`.
2. Заблокировать исходную и целевую комнаты через `SELECT FOR UPDATE`, по ID.
3. Заблокировать существующую бронь и повторно проверить владельца/разрешение.
4. Проверить, что текущая комната входит в уже заблокированные; иначе отклонить
   устаревший перенос. Дополнительные комнаты после брони не блокируются.
5. Проверить обязательную переданную revision и сравнить её с текущей.
   Для редактирования/подтверждения дополнительно сравнить снимок модели.
   Идемпотентный повтор отмены обрабатывается без записи по контракту D.
6. Проверить статус, активность комнаты, время, конфликт и необходимость VIP-согласования.
7. Сохранить запись, увеличив `revision`; завершить транзакцию.

Отмена использует актуальные поля записи и не копирует поля устаревшего объекта.
Для изменения активной записи обязательна совпадающая revision. Повторная
отмена уже отменённой записи с корректной равной/старой версией успешна без
повторной записи. Отсутствующая, неверная или будущая версия даёт отказ.
После отмены изменение или подтверждение запрещено.
Отклонение администратором допустимо только для ожидающей заявки.

Преимущество отмены без учёта версии осталось только в историческом поведении
этапа 3. В этапе 5.2, если сначала подтверждение изменило версию, прежняя отмена
отклоняется. Если сначала
выполнена отмена, подтвердить уже нельзя. Идемпотентный повтор отмены состояния
`cancelled` остаётся успешным без записи по таблице D в BUSINESS_RULES.md.

Сохранена возможность отменить завершённую встречу, ранее существовавшая в
модели/HTML: теперь она одинакова и в API. Редактирование завершённых встреч
запрещено. Новая VIP-заявка и перенос/изменение времени VIP требуют `pending`.

Массовые административные действия выполняют отдельную транзакцию для каждой
записи и сообщают об ошибках отдельных операций. Нельзя оборачивать несколько
операций над произвольными комнатами в собственную общую транзакцию или заранее
блокировать Booking: это нарушает контракт порядка блокировок. Для будущей
атомарной пакетной операции нужно заранее блокировать полный набор комнат по ID,
затем полный набор броней по ID.

## Защита от устаревших данных — текущее состояние

В экземпляре модели сохраняется снимок, полученный из БД. Устаревший `save()`,
в том числе с `update_fields`, отклоняется. Частичное сохранение не переносит в
базу изменения полей, не перечисленных в `update_fields`.

HTML и Django Admin передают скрытую версию записи. API возвращает `revision`;
при PUT/PATCH клиент должен отправить полученное значение. Несовпадение даёт
ошибку валидации (API 400, HTML ошибка формы). Отправленная версия не может
изменить счётчик напрямую.

Прежняя совместимость изменения без версии удалена в этапе 5.2. Создание
нового бронирования не требует revision; существующее требует её во всех
путях, включая `Booking.save(revision=...)` и `persist(..., revision=...)`.
Собственная панель передаёт `revision`, Admin actions — `revision_<id>` каждой
показанной строки. `select_across=1` для подтверждения/отклонения запрещён.
`required=False` в объявлении API-поля обслуживает создание; validate()
обязательно проверяет наличие версии для PUT и частичного PATCH.

## Технический контракт и оставшиеся задачи

Пункты 1–5 реализованы в этапе 5.2. Пункты 6–7 описывают будущую работу.

1. Запрос изменения/подтверждения/отклонения/отмены передаёт ожидаемую revision.
   При отсутствии или некорректном формате — ошибка валидации. Нельзя подменять
   отсутствующую версию текущей из БД или считать серверный снимок эквивалентом
   версии ранее открытой страницы.
2. Транзакция получает блокировки в прежнем порядке: комнаты по ID, затем
   бронирования. После проверки доступа и актуального состояния сравнивается
   клиентская revision. Несовпадение запрещает изменение активной записи.
3. Для уже отменённой записи корректная равная либо старая revision допускает
   успешный повтор отмены без записи, увеличения версии и нового события.
   Отсутствующая/некорректная или будущая версия не допускается. Эта ветка
   определяется под блокировкой; восстановление отменённой брони запрещено.
4. При массовом согласовании проверяется версия каждой просмотренной заявки.
   Сохраняются отдельные транзакции и отчёт о частичных отказах. Нельзя брать
   версии только после POST. Атомарность всей произвольной пачки не обещается.
5. Внутренний сброс согласования при смене типа комнаты использует актуальные
   версии под блокировками и увеличивает их. Он не требует клиентских версий
   всех затронутых броней и не легализует подмену версии при ручном подтверждении.
6. Повтор создания по одному ключу и данным возвращает исходный результат,
   иной payload отклоняется. Область ключа — пользователь и операция создания.
   Резервирование ключа и фиксация брони должны предотвращать конкурентные дубли
   и ложный результат после rollback. Существующее exclusion constraint остаётся.
   В 5.3 реализован порядок ключ → комнаты → бронь; автоматического TTL нет.
   Алгоритм резервирования и ошибки описаны ниже.
7. Каскадное удаление должно быть закрыто политикой хранения. `PROTECT` для
   связей Booking — рекомендованный механизм будущей миграции; он дополняет
   ограничения Admin, а не заменяется ими. Сроки очистки и обезличивание не решены.

Нельзя автоматически повторять запись после неизвестного результата commit,
считая, что она не состоялась. Для создания нужен тот же ключ; для изменения —
повторное чтение состояния и обработка revision. После rollback нельзя полагаться
на изменённый объект Python как на состояние БД. Журнал бизнес-событий, когда
будет внедрён, должен фиксироваться согласованно с изменением состояния.

## ORM и защита базы

`update`, `bulk_create`, `bulk_update`, `update_or_create` запрещены у обычного
и базового менеджера Booking. Последний метод Django блокирует бронь раньше
комнаты и потому также запрещён. Пакетные действия используют операции выше.
Существующий тест отмены старой встречи сохранён; его фикстура теперь создаётся
при замороженном времени, а не через обходной `update()`.

Приватные ORM-методы, исторические модели миграций и raw SQL — доверенные
инструменты сопровождения, а не публичный API. PostgreSQL дополнительно
защищает от пересечений даже при прямом SQL. Она не проверяет Django permissions
или весь жизненный цикл статуса для произвольного SQL.

Миграция `0005_booking_concurrency` добавляет `revision` и для PostgreSQL
ограничение `booking_no_active_overlap`:

```sql
EXCLUDE USING gist (
  room_id WITH =,
  tstzrange(start_time, end_time, '[)') WITH &&
) WHERE (status IN ('pending', 'confirmed'))
```

Это SQL-эквивалент PostgreSQL `ExclusionConstraint`. Он оформлен условной
database-only операцией миграции, чтобы не выполнять PostgreSQL DDL и range-
валидацию на SQLite. Ограничение не отражено в `Meta.constraints`; его наличие
проверяется отдельным PostgreSQL-тестом прямой вставки. Для равенства room_id
в GiST требуется расширение `btree_gist`.

Интервалы полуоткрытые: соседние встречи разрешены, отменённые не занимают слот.
Известное нарушение exclusion constraint преобразуется в ошибку валидации;
остальные IntegrityError не маскируются.

## Безопасное применение миграции

На рабочей базе в этой задаче ничего не запускалось. Перед её применением:

1. Сделать резервную копию и проверить восстановление на копии базы.
2. На копии проверить некорректные интервалы и пересечения активных броней.
   Миграция остановится с ошибкой при их наличии и не исправляет данные сама.
3. Убедиться, что `btree_gist` доступно и у миграционной роли есть право установки,
   либо попросить DBA установить расширение заранее.
4. Остановить запись в согласованное окно обслуживания: добавление ограничения
   сканирует таблицу и требует блокировки. Оценить время на копии данных.
5. Применить `python manage.py migrate` и проверить ограничение и приложение.

Откат снимает ограничение и поле revision; расширение не удаляется, поскольку
может использоваться другими таблицами. SQLite получает только поле/метаданные.

## Границы

В этапе 4 управление типом и активностью комнаты включено в слой операций:
сначала блокируется комната, затем затронутые брони по ID. При переходе на VIP
незавершённые подтверждённые брони требуют нового согласования. Подробности
и актуальный отчёт тестирования — в `BUSINESS_RULES.md`.

Удаление комнат/пользователей с каскадом, внешние SQL-скрипты и транзакции,
нарушающие описанный порядок, не являются операциями этого слоя.
В 5.3 повтор создания после неизвестного COMMIT защищён ключом: повторять
нужно те же данные с тем же ключом. Существующие внутренние create/save без
ключа остаются доверенными инструментами, не HTTP-путями. Полная защита
исторических данных от удаления остаётся отдельной задачей. Контракты C/E в BUSINESS_RULES.md
задают целевое поведение. В этапе 5.2 обязательная revision реализована без
новых миграций. Полный прогон: PostgreSQL 17.12 на порту 55439 — 174 успешно;
SQLite — 156 успешно, 18 пропусков. Из 31 нового теста 4 проверяют конкуренцию
именно на PostgreSQL. Детали результатов — в BUSINESS_RULES.md.

## Этап 5.3: транзакция создания и повтор

HTTP-входы: API, HTML и добавление в Django Admin → `create_once()` →
`booking_idempotency.create()`. Внутренний `create()`/`persist()` сохраняет прежние
правила и блокировки. Его нельзя использовать для обработки HTTP-создания без ключа.

1. Проверить ключ, синтаксис datetime и права. Нормализовать фактические параметры.
2. Начать atomic на той же базе, где хранится Booking.
3. В savepoint вставить резервирование BookingCreationRequest. Немедленное
   UNIQUE(actor, operation, key) сериализует одинаковые ключи даже до появления брони.
4. На PostgreSQL только вокруг вставки используется транзакционный lock_timeout=5000ms.
   При успехе прежнее значение восстанавливается; при ошибке оно восстанавливается
   откатом savepoint. Глобальные настройки и настройки подключения не меняются.
5. Конфликт конкретного уникального ограничения перехватывается после rollback
   savepoint. В Read Committed следующий SELECT видит зафиксированный результат.
   Другие IntegrityError не маскируются под replay.
6. Для повтора проверить параметры и актуальный доступ, вернуть первоначальный
   снимок. Не выполнять повторно проверки прошлого времени/активности/пересечений.
7. Для новой операции выполнить обычные room-lock, full_clean, INSERT Booking,
   затем сохранить ссылку и снимок в записи ключа. Исключение откатывает обе записи.
8. COMMIT общей транзакции. Admin дополнительно включает LogEntry в свою внешнюю
   atomic; повтор пропускает log_addition. Ответ отправляется после завершения транзакции.

Порядок блокировок: ключ → комнаты по PK → бронь. Операции изменения/согласования
не захватывают ключи. Запрещены предварительные room/booking locks перед create_once
и произвольные пакеты таких операций в общей внешней транзакции. Нового порядка
захвата нескольких комнат/броней этот этап не вводит.

Незавершённое резервирование не фиксируется отдельно; нет on_commit-финализации,
отдельного соединения или кеша. Обычные ORM-записи и удаление результатов запрещены.
Приватные ORM/SQL-инструменты остаются доверенными: не используйте их для обхода.

При потере подтверждения COMMIT база содержит обе записи или ни одной. После
восстановления соединения повтор с тем же ключом возвращает снимок или выполняет
создание. Ошибка ожидания ключа даёт 503; клиент сохраняет ключ. Не меняйте ключ
автоматически после сетевой ошибки. Технические HTTP-логи могут фиксировать попытки,
но replay не повторяет сохранение брони, сигналы save или LogEntry.

Миграция 0006 работает на PostgreSQL и SQLite, расширений не требует. Тесты гонок
используют отдельные соединения и TransactionTestCase; барьер стоит перед вставкой
ключа. Барьер перед room-lock для одинакового ключа непригоден: второй запрос ещё
ждёт первый ключ. SQLite проверяет функциональность, а не корректность row locks.
