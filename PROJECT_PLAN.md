# План работ и оценка сроков — MeetingRoomBooking

Документ фиксирует плановую оценку этапов для учебного кейса ИСП49. Значения трудозатрат — оценка для планирования, а не табель фактически затраченного времени. Фактические реализации и результаты проверок приведены в `DELIVERY.md`.

## Этапы

| Этап | Плановая оценка | Результат / критерий завершения |
|---|---:|---|
| 1. Анализ требований и проектирование | 0,5 дня | Согласованы сценарии бронирования, ограничения 1–4 часа, роли, VIP и критерии приёмки; подготовлены правила и архитектурная схема |
| 2. Модель данных и основная бизнес-логика | 1 день | Реализованы комнаты, бронирования, пользователи/роли; проверяются интервалы, конфликты, транзакции и история |
| 3. Интерфейс, API и разграничение доступа | 1 день | Доступны каталог, расписание, авторизация, история, API и административные операции; отрицательные проверки прав проходят |
| 4. Модификации VIP и CSV | 0,5 дня | VIP-заявки проходят согласование; CSV экспортирует записи с фильтрами по комнате и диапазону дат |
| 5. Среда, Docker и CI | 1 день | Воспроизводимый Compose-стенд, health checks, GitHub Actions, тесты, линтинг и сборка production image |
| 6. Мониторинг и нагрузочные проверки | 0,75 дня | Prometheus, Alertmanager, Grafana; проверки метрик и алертов; нагрузочные сценарии 100/200 RPS и 1000 VU |
| 7. Регрессия, документация и приёмка | 0,75 дня | Регрессионные и HTTP E2E-проверки, реестр дефектов, руководство, отчёты и сценарии демонстрации |

**Суммарная плановая оценка: около 5,5 рабочих дней.** Приоритет отдаётся целостности данных, конфликтам бронирования, доступу и воспроизводимости проверок; необязательные production-функции выносятся за рамки MVP.

## Основные риски и меры снижения

| Риск | Возможное последствие | Мера снижения / проверка |
|---|---|---|
| Конкурентные запросы на один интервал | Двойное бронирование | Транзакционная логика и ограничение пересечений PostgreSQL; конкурентные тесты |
| Потеря или незаметное изменение истории | Невозможность аудита действий | Append-only AuditEvent, запрет штатного удаления, миграционные guards, тестовый backup/restore |
| Ошибка разграничения прав | Пользователь получает чужие административные действия | Django Groups/Permissions, серверные проверки и отрицательные тесты |
| Отказ PostgreSQL или Redis | Недоступность функций или потеря временного кэша | Health checks, SQL readiness, Redis как некритичный cache, сценарии восстановления |
| Недостаточная производительность | Рост задержки и ошибок при увеличении нагрузки | Отдельные read-only прогоны 100/200 RPS и k6 до 1000 VU; ограничения результатов явно фиксируются |
| Утечка секретов | Компрометация базы или приложения | Секреты вне Git, `.env` в `.gitignore`, тестовые credentials только в изолированных стендах |
| Ошибка развёртывания или миграции | Простой или повреждение данных | Отдельные профили окружений, ручная проверка миграций, backup перед опасными изменениями |
| Неполная приёмка документации | Замечания проверяющего на сдаче | Сверка матрицы требований и фактическая рецензия наставником/одногруппником; отзыв нельзя подменять внутренней проверкой |

## Контрольные точки

1. **MVP:** пользователь видит комнаты и занятость, создаёт и отменяет бронь, конфликт отклоняется.
2. **Расширение:** VIP-согласование, роли/permissions, CSV и API.
3. **Инфраструктура:** Docker, health checks, CI и production image artifact.
4. **Надёжность:** тесты PostgreSQL, мониторинг, алерты, нагрузочные профили.
5. **Сдача:** регрессия, дефектный реестр, руководство, матрица требований и фактическая рецензия.

Автоматический CD в Render, длительный SLA 99,9%, внешняя доставка уведомлений и смешанный write-нагрузочный профиль остаются отдельными задачами; их нельзя считать выполненными только на основании сборки или read-only тестов.
