# Краткое техническое задание — MeetingRoomBooking

## 1. Цель

Разработать веб-приложение для бронирования переговорных комнат офиса. Пользователь должен видеть доступность помещений, создавать и отменять бронирования, просматривать историю; сотрудник согласует VIP-заявки; администратор управляет комнатами и правами доступа.

## 2. Участники и роли

- **Пользователь:** просмотр каталога и занятости, собственные бронирования, отмена и история.
- **Согласующий сотрудник:** просмотр административных заявок, подтверждение/отклонение VIP-бронирований в пределах выданных permissions.
- **Администратор:** управление комнатами, пользователями, группами и разрешениями.
- **Наблюдатель журнала:** просмотр аудита при наличии отдельного разрешения.

Роли представлены отдельной моделью `rooms.Role`, связанной один-к-одному с `auth.Group`. Модель `Role` хранит код и описание; имя и разрешения берутся из связанной группы, которая остаётся единым источником прав Django (`auth.Permission`).

## 3. Функциональные требования

1. Публичный каталог активных переговорных с названием, описанием, вместимостью, типом и фотографией.
2. Просмотр занятости по комнатам и часовым слотам.
3. Создание бронирования на 1–4 часа в рабочем интервале 08:00–20:00 и в пределах горизонта 30 дней.
4. Проверка пересечений на сервере и в PostgreSQL; активные `pending` и `confirmed` интервалы не могут пересекаться для одной комнаты.
5. Отмена бронирования с сохранением записи в истории; отменённая запись не редактируется и не активируется повторно.
6. VIP-заявка получает статус ожидания; подтверждение/отклонение выполняет сотрудник с соответствующим permission.
7. Просмотр собственных бронирований и истории; административные действия журналируются.
8. Администратор может создавать, изменять, архивировать и восстанавливать комнаты в пределах разрешений.
9. CSV-экспорт бронирований с фильтрами по комнате и диапазону дат.
10. REST API предоставляет каталог комнат, бронирования, отмену, историю и административный CRUD комнат; OpenAPI-схема доступна отдельно.

## 4. Нефункциональные требования

- Целевой p95 ответа: не более 200 мс в согласованном тестовом сценарии.
- Целевой error rate: не более 0,1%.
- Целевая доступность: 99,9%; для подтверждения требуется длительное наблюдение, а не короткий тест.
- Аутентификация, серверная проверка permissions, безопасная обработка входных данных и конфликтов.
- Аудит изменений и защита истории от штатного удаления.
- Health/readiness endpoint, резервное копирование и проверка восстановления.
- Измерение HTTP requests/errors/latency, PostgreSQL connections и состояния зависимостей.

## 5. Технологические и эксплуатационные ограничения

- Backend: Python 3.14.2, Django 6.0.10, Django REST Framework.
- Database: PostgreSQL 17; Redis используется как необязательный некритичный cache, бизнес-данные и сессии остаются в PostgreSQL.
- Контейнеризация: Docker Compose, Gunicorn и Nginx; отдельный облачный профиль Render + Neon.
- Рабочее хранение времени — UTC; отображение использует TIME_ZONE приложения.
- Репликация PostgreSQL и автоматический failover в текущем учебном стенде не настроены.
- Автоматический deploy в Render выключен; GitHub Actions проверяет изменения и сохраняет production image artifact.
- Нагрузочные измерения read-only не доказывают производительность записи бронирований или SLA за длительный период.

## 6. Критерии приёмки

- Пользователь может создать/отменить бронь, просмотреть историю; конфликт пересекающихся интервалов отклоняется.
- VIP-заявка ожидает решения и может быть подтверждена/отклонена уполномоченным сотрудником.
- CSV-фильтры по комнате и датам применяются корректно; формулы в текстовых ячейках нейтрализуются.
- Permissions ограничивают административные операции; аудит сохраняет изменения.
- Критические модули имеют покрытие не ниже 70%; unit/integration/HTTP E2E и регрессионные тесты проходят.
- CI при push/PR выполняет тесты, статические проверки, контейнерную сборку и сохраняет Docker image artifact.
- Grafana/Prometheus/Alertmanager provisioned, метрики и тестовый alert проверяются автоматически.
- Нагрузочные отчёты содержат фактические RPS, ошибки и latency; ограничения тестовых сценариев указаны явно.
