# REST API MeetingRoomBooking

## Статус документа

Документ описывает API после этапа 5.2: обязательная revision реализована
для изменения и отмены. Раздел идемпотентности создания описывает будущую
реализацию, которой в коде пока нет. Источник бизнес-правил —
[BUSINESS_RULES.md](BUSINESS_RULES.md). Новых endpoints в этапе 5.2 нет.

## Действующий API после этапа 5.2

Базовый адрес: `/api/`. Формат обмена — JSON. Для запросов, изменяющих данные, используйте авторизованную Django session (и CSRF-токен при cookie-аутентификации).

### Переговорные

- `GET /api/rooms/` — список активных комнат.
- `GET /api/rooms/{id}/` — сведения о комнате.
- `POST /api/rooms/` — создать комнату: активный staff с `rooms.add_room`.
- `PUT/PATCH /api/rooms/{id}/` — изменить комнату: активный staff с `rooms.change_room`.
- `DELETE /api/rooms/{id}/` — архивировать комнату: активный staff с `rooms.change_room`; бронирования сохраняются.
- `GET /api/rooms/{id}/availability/?date=YYYY-MM-DD` — занятые интервалы на выбранную дату. Возвращаются только время начала и окончания, без личных данных участников.

Список активных комнат, сведения и свободные интервалы доступны без авторизации.
Для списка/сведений `include_archived=true` требует активного staff с
`rooms.view_room`. Один `is_staff` не даёт права изменения каталога. Архивирование
через API уже сохраняет историю; текущие возможности физического удаления
через Django Admin пока не обеспечивают целевой контракт хранения.

### Бронирования (только авторизованный пользователь)

- `GET /api/bookings/` — только собственные бронирования.
- `GET /api/bookings/{id}/` — подробности собственного бронирования.
- `POST /api/bookings/` — создать бронирование.
- `PUT /api/bookings/{id}/` — полностью изменить дату, время и/или комнату (для PUT нужны все обязательные поля).
- `PATCH /api/bookings/{id}/` — частично изменить дату, время или комнату.
- `POST /api/bookings/{id}/cancel/` — отменить ожидающую, подтверждённую,
  начавшуюся или завершённую встречу; повтор отмены успешен без новой записи.

Пример данных создания (дату нужно заменить на подходящую будущую дату
в пределах 30 дней; время указано в UTC):

```json
{
  "room": 1,
  "start_time": "2026-12-01T10:00:00Z",
  "end_time": "2026-12-01T12:00:00Z"
}
```

`status`, `user` и `created_at` нельзя менять через API; передача статуса
не предоставляет права подтверждения. Стандартные комнаты подтверждаются
автоматически, VIP-заявки создаются в `pending`. Подтверждение выполняется
отдельно в административных интерфейсах сотрудником с `rooms.change_booking`.

При создании или переносе проверяются активность комнаты внутри транзакции,
рабочие часы 08:00–20:00 в UTC, длительность 1–4 часа включительно, отсутствие
начала в прошлом, горизонт сегодня + 30 дней включительно и пересечений
с `pending`/`confirmed`. Промежуточное время допустимо. Соседние интервалы
разрешены; `cancelled` не занимает время. ISO datetime со смещением приводится
к зоне сайта; без смещения трактуется как UTC. Дата availability обязательна
и ограничена тем же горизонтом. Неверные даты дают 400.

Ответ содержит серверную `revision`. Она обязательна при PUT, PATCH и POST
отмены. Пропуск, null, пустое или некорректное значение дают 400. При создании
исходная версия не требуется; счётчик назначает сервер. Версия — целое
0–2147483647 или десятичная строка до 10 цифр; boolean, float, дробная и
экспоненциальная запись не принимаются. Сравнение повторяется внутри транзакции
после получения блокировок. Устаревшая версия активной записи даёт 400.
Повтор отмены уже отменённой записи описан ниже.

Текущее редактирование комнаты/времени в целевой VIP-комнате возвращает `pending`.
Перенос подтверждённой VIP-встречи в обычную сейчас сохраняет `confirmed`;
контракт 5.1 требует `pending` и для этого переноса. Восстановление отменённой
брони и редактирование завершённой запрещены. Обычная → VIP при изменении типа
самой комнаты сбрасывает согласование незавершённых встреч с ростом revision;
обратная смена типа не подтверждает ожидающие заявки.

### Фильтры списка бронирований

- `?status=pending|confirmed|cancelled`
- `?period=upcoming|past`
- `?room=ID`
- `?date_from=YYYY-MM-DD&date_to=YYYY-MM-DD`
- `?ordering=start_time|-start_time|created_at|-created_at`

Пример: `/api/bookings/?period=upcoming&status=confirmed&ordering=start_time`.

Фильтры дат используют строгий `YYYY-MM-DD`; обратный период даёт 400.
Текущие списки не имеют пагинации. Параметр поиска `q` API не поддерживает.
Ошибочные значения остальных фильтров пока не имеют единого строгого контракта;
аудит выявил необработанные ошибки некоторых значений `room`. Это не исправлено
изменением документации и требует отдельного задания.

### Текущие коды ответов

- `200` — успешно;
- `201` — ресурс создан;
- `204` — комната архивирована;
- `400` — неверные данные, конфликт времени или недопустимая операция;
- `403` — недостаточно прав, ошибка CSRF либо отсутствие аутентификации
  при текущей SessionAuthentication; ответ 401 текущим способом не гарантируется;
- `404` — объект отсутствует или не принадлежит текущему пользователю.

Ошибки могут иметь поля `booking`, имя конкретного поля или `detail`.
Единый формат и машинные коды ещё не утверждены. Для ошибки версии используется
400; обязательная версия реализована, HTTP 409 не вводился.

### Администрирование

Управление комнатами и всеми бронированиями выполняется через `/admin/` пользователями с соответствующими правами Django Admin. Для бронирований доступны фильтры, поиск, подтверждение и отклонение ожидающих заявок, а также экспорт выбранных записей в CSV.

Собственная панель находится по `/management/`. Для согласования требуется
`rooms.change_booking`, для экспорта — отдельное `rooms.export_booking`,
для просмотра и других действий — соответствующие permissions. Группы
и их назначения не меняются в этапе 5.1.

## Контракт этапа 5.1: реализованные и будущие части

### Изменение и согласование существующей записи

Этот подраздел реализован в этапе 5.2, кроме отдельно отмеченной ниже
будущей политики переноса VIP → обычная.

Для PUT/PATCH, отмены, подтверждения и отклонения обязательна версия, полученная
при просмотре заявки. Создание новой записи исходной revision не требует.
Отсутствующее/пустое/некорректное значение — ошибка валидации; несовпадение
запрещает изменение состояния. Нельзя подставлять актуальную версию на сервере
вместо клиентской. Те же правила действуют для HTML, Django Admin и собственной
панели; массовое согласование передаёт версию каждой просмотренной заявки.

Пример тела PATCH: изменить комнату, если при чтении была получена версия 7:

```json
{"room": 2, "revision": 7}
```

Пример тела отмены по целевому контракту:

```json
{"revision": 7}
```

Число 7 иллюстративно: использовать нужно значение ответа для конкретной брони.
Счётчик изменяет только сервер. После отказа необходимо заново получить данные
и осознанно повторить действие; автоматическая замена версии запрещена.

Отмена активной записи требует совпадения revision. Если запись уже `cancelled`,
корректная равная или более старая revision даёт успешный повтор без изменения,
роста версии и нового события. Отсутствующая, некорректная или будущая версия
отклоняется и в этом случае. Доступ проверяется всегда. Полная таблица — раздел D
BUSINESS_RULES.md. Отменённую запись нельзя восстановить, завершённую можно отменить.

Подтверждение VIP остаётся ручным и только для просмотренных параметров/версии.
В Admin форма изменения передаёт `expected_revision`, массовые действия —
`revision_<id>` каждой строки; собственная панель — `revision`. Массовые
подтверждение/отклонение всех результатов поиска (`select_across=1`) запрещены;
следует выбирать показанные заявки. Ошибки отдельных записей не отменяют
успешные операции остальных выбранных записей.
Сброс в `pending` при переносе подтверждённой VIP-встречи в обычную комнату —
оставшаяся будущая часть контракта, не изменение этапа 5.2. Пользовательский API
не получает права записи статуса или нового endpoint подтверждения.

### Идемпотентность создания и HTML-совместимость — ещё не реализовано

Будущий ключ связан с авторизованным пользователем и операцией создания.
Повтор ключа с теми же данными возвращает первоначальный результат, иной payload
отклоняется. Конкурентные повторы не создают дубли. Последующая отмена/перенос
брони не превращают повтор создания в новый запрос. Для нового намерения
используется новый ключ. Возвращённая первоначальная revision может устареть:
перед редактированием нужно получить актуальную запись.

API-клиент сохраняет ключ между сетевыми повторами; HTML-форма передаёт скрытый
ключ, сохраняемый при повторе одной отправки. Оба интерфейса используют общий
механизм и область ключей, включая повтор между интерфейсами. JSON и HTML-редирект
могут различаться, но указывают на один результат создания, без повторных событий.

Заголовок `Idempotency-Key` и поле `idempotency_key` предложены, но ещё не
утверждены как транспорт и не реализованы. Срок хранения не установлен.
Нельзя обещать распознавание повторов без ключа или после несогласованного
удаления записи ключа. Обязательность ключей для старых API-клиентов,
канонизация payload, обработка ошибок и выполняющегося запроса — открытые
решения из раздела «Решения, требующие дополнительного согласования» BUSINESS_RULES.md.

### Изменения, влияющие на совместимость

| Изменение и статус | Что потребуется от клиента |
|---|---|
| Обязательная revision для PUT/PATCH и отмены — реализовано | Сохранять полученную версию и передавать её; старые запросы без неё теперь ошибочны |
| Версии в административных действиях — реализовано | Передавать версии просмотренных записей, включая каждую запись массового действия |
| Отмена не перезаписывает свежую активную запись — реализовано | После конфликта заново прочитать состояние и принять решение |
| Перенос подтверждённой VIP в обычную даёт pending — будущая задача | При её внедрении не ожидать сохранения прежнего согласования |
| Ключи создания — будущая задача | Согласовать переход старых клиентов; будущий HTML должен передавать ключ |

Код этапа 5.2 уже требует revision без режима совместимости. Порядок его
развёртывания у внешних клиентов согласуется отдельно. Будущий переход
на 409 и единый машинный формат ошибок не утверждены. Пагинация, ключи создания,
новые группы и изменения схемы БД в этапе 5.2 не вводились.
