# Подтверждение VIP-бронирований

## Статус и источник правил

Утверждённые бизнес-контракты этапа 5.1 находятся в
[BUSINESS_RULES.md](BUSINESS_RULES.md), разделы A–E. В этапе 5.1 изменена только
документация. В этапе 5.2 реализована обязательная версия для изменения,
отмены и согласования во всех интерфейсах, включая массовые действия.
Остальные будущие изменения отдельно отмечены ниже.

## Фактическое поведение после этапа 4

Правило находится в модели Booking и применяется при валидации и сохранении
через HTML, REST API и Django Admin. Миграция для этапа 2 не требуется.

- Новая обычная бронь получает `confirmed`, новая VIP-заявка — `pending`.
- Перенос активной брони в другую VIP-комнату или изменение времени VIP-встречи
  возвращает заявку в `pending`, включая ранее подтверждённую встречу.
- Повторное сохранение без изменения комнаты и времени сохраняет согласование.
- Подтверждение неизменённой заявки `pending → confirmed` выполняется отдельно
  в собственной панели или Django Admin сотрудником с `rooms.change_booking`.
- HTML-формы и пользовательский API не принимают статус от клиента: переданный
  `status` игнорируется. Это относится и к сотруднику в пользовательском API.
- Ожидающую, подтверждённую, начавшуюся и завершённую встречу можно отменить.
  Отменённая запись не редактируется и не
  возвращается в активный статус; для нового бронирования создаётся новая запись.
- Перенос между обычными комнатами сохраняет статус. Перенос ожидающей заявки
  из VIP в обычную комнату также сохраняет `pending`, как до исправления:
  автоматическое подтверждение такого переноса не добавлялось.
- Перенос подтверждённой VIP-встречи в обычную комнату сейчас сохраняет
  `confirmed`. Это расхождение с целевым контрактом этапа 5.1, а не разрешённый
  будущий обход повторного согласования.

В HTML-форме редактирования добавлен выбор активной комнаты. POST без поля
`room` сохраняет прежнюю комнату для совместимости с изменением только времени.
API редактирования не позволяет переносить завершённые записи, как и HTML.

Проверки прав этапа 1 и назначение групп не менялись. В этапе 2 схема базы,
CSS и дизайн не менялись. Тесты выполняются с изолированными конфигурациями
SQLite и PostgreSQL, без чтения `.env` и подключения к рабочей базе.

Этап 3: запись выполняется через `rooms.booking_operations`, массовые ORM-
операции запрещены, введена версия записи и PostgreSQL-ограничение пересечений.
Порядок блокировок, миграция и результаты конкурентных проверок описаны в
`CONCURRENCY.md`.

Этап 4: смена типа комнаты на VIP атомарно переводит ещё не завершённые
подтверждённые встречи в `pending` с увеличением revision. Завершённые и
отменённые записи сохраняются. Переход VIP → обычная не подтверждает заявки
автоматически. Текущие правила времени и результаты проверки — в `BUSINESS_RULES.md`.

## Утверждённый контракт и реализация в этапе 5.2

Проверки версий, в том числе в массовых действиях, реализованы. Расширение
сброса согласования при переносе VIP → обычная из пункта 3 остаётся будущей
задачей: этап 5.2 посвящён обязательной revision, а не изменению этой политики.

1. Подтверждение остаётся отдельным ручным действием активного сотрудника
   с `rooms.change_booking`. Пользовательский API не получает возможности
   подтверждения от наличия у пользователя `is_staff`.
2. Сотрудник подтверждает именно просмотренную revision и параметры заявки.
   Отсутствующая/некорректная версия даёт ошибку, несовпадение — отказ без записи.
   Нельзя обновить revision автоматически и подтвердить уже изменённую заявку.
3. Изменение комнаты или времени VIP-заявки требует `pending`; перенос
   подтверждённой VIP-встречи в обычную комнату также требует `pending` по
   формулировке задания 5.1. Это намеренное отличие контракта от текущего кода.
4. Массовое согласование содержит отдельную просмотренную версию каждой
   выбранной заявки. Устаревшие элементы отклоняются с явным результатом;
   корректные могут выполниться в отдельных транзакциях. Согласование всех
   результатов поиска без ознакомления с их параметрами недопустимо.
5. Проверки повторяются внутри транзакции с прежним порядком блокировок.
   Отказ не меняет статус, revision и не создаёт событие изменения состояния.
6. При гонке подтверждения и отмены нельзя применять старую revision к активной
   записи. Подтверждение первым делает прежний запрос отмены устаревшим;
   отмена первой запрещает подтверждение. Повтор отмены уже отменённой записи
   обрабатывается по таблице D в BUSINESS_RULES.md без нового изменения/события.

Не меняются рабочие часы 08:00–20:00, UTC, длительность 1–4 часа, горизонт
30 дней, разрешение промежуточного времени, проверка активности под блокировкой,
защита пересечений и существующая система Permissions/Groups. Роль администратора
не даёт права обходить бизнес-правила согласования и сохранения истории.

В этапе 5.2 формы требуют revision; собственная панель передаёт её в скрытом
поле, Admin actions получают `revision_<id>` для каждой показанной строки.
Массовые подтверждение/отклонение с `select_across=1` запрещены: следует выбрать
заявки на просмотренной странице. Пропущенная/неверная версия конкретной строки
даёт отказ по этой записи без автоматического обновления её версии.
Открытые решения перечислены в BUSINESS_RULES.md и [API_GUIDE.md](API_GUIDE.md).
Новых миграций для обязательной revision нет. Существующие Permissions/Groups
сохранены. Ниже описана добавленная в 5.3 идемпотентность создания.

## Этап 5.3: повтор создания VIP-заявки

HTML, API и Django Admin создают заявку через create_once с обязательным ключом.
Новая VIP-бронь получает pending, в том числе при переданном confirmed.
Повтор с тем же ключом возвращает первоначальный снимок, даже если заявка уже
согласована, перенесена или отменена. Он не меняет её текущий статус/revision,
не восстанавливает отменённую бронь и не повторяет LogEntry Admin.

Для нового намерения нужен новый ключ. Для подтверждения существующей заявки
по-прежнему нужны rooms.change_booking и актуальная просмотренная revision.
Переход комнаты в VIP может сделать первоначальный снимок confirmed устаревшим;
это не согласование актуальной заявки. Перед изменением/подтверждением нужно
снова получить текущее состояние. Политика переноса VIP → обычная в 5.3 не менялась.
